The factory has been running since Module 1. You governed its tool calls in Module 3, taught it in Module 4, and ran it headless in a pipeline in Module 5. This module turns all of that into output: a shipped microservice, promoted to production, consumed as a new governed tool by the agent that originally asked for it.

The request comes from Morgan, ACME Financial's ops manager — and it is the most universal request in the enterprise. Every Monday, Morgan runs the week out of a spreadsheet: export order data from `orders-api` (a system IT exposed years ago), stitch the exports together with VLOOKUPs, eyeball which orders are stuck, hand-build a weekly summary, paste it into chat. The data exists behind endpoints; the *answers* don't. The old fix — "just give me a summary endpoint" — sits in IT's backlog measured in quarters.

Today's process: file the intent in Mattermost to a dev agent, watch its governed tool calls scaffold the service and open a pull request, merge it, and let the supply chain build, sign, scan, and promote. Then the move that makes it Morgan's Monday: register the shipped service behind the MCP gateway, and the assistant Morgan already talks to answers the Monday question with a governed tool call — numbers, not VLOOKUPs, with an audit entry for every step.

One more thing, and it is the point of the whole lab: you have already *used* this capability. The `metrics_stuck_orders` tool your skill declared in Module 4 and your pipeline called in Module 5 is the platform's own copy of exactly this service, built exactly this way. In this module you build yours — and watch the factory pave the road it runs on.

5 exercises, about 60 minutes total. Each has a clean stopping point.

== Learning objectives

By the end of this module, you'll be able to:

* Hire a second agent from the same Developer Hub template and explain how a different brief composes a materially different capability set
* Commission a microservice through a Mattermost intent and trace the dev agent's governed Gitea tool calls to your org
* Read a supply-chain PipelineRun and confirm the build, sign, and scan stages completed before GitOps promoted the service
* Register a newly shipped service behind the MCP gateway using an MCPServerRegistration resource
* Trace the complete loop — a governed tool call from the requesting agent, through the gateway, to the service the factory just built — and read the audit entry that proves it happened

== Exercise 3: Merge and ship through the supply chain

The dev agent opened the pull request. You own the merge decision — the same pattern you practiced in Module 2: the diff is readable, the source is the agent's tool calls, and the merge is the moment of record. The scaffold conforms to the platform's *golden-path service contract* — a versioned skill every agent on your seat carries (Module 4's delivery mechanism, working for Module 6): Dockerfile at the root, port 8080, the deployment manifest shape, and the supply-chain pipeline definition already included under `.tekton/`.

. Wire your repository into the supply chain *before* merging, so the merge event lands on a listening pipeline. The platform side is already standing — an org-level webhook on your Gitea org feeds the cluster's Pipelines-as-Code controller — so your half is one resource: a `Repository` that tells Pipelines-as-Code this repo's runs belong in your namespace, authenticated by your own seat credentials:
+
[source,bash,role="execute",subs="+attributes"]
----
cat <<EOF | oc apply -n {user}-agent-workspace -f -
apiVersion: pipelinesascode.tekton.dev/v1alpha1
kind: Repository
metadata:
  name: order-metrics
spec:
  url: {gitea_url}/{user}-agents/order-metrics
  git_provider:
    type: gitea
    url: {gitea_url}
    secret:
      name: {user}-gitea-token
      key: GITEA_TOKEN
    webhook_secret:
      name: pac-gitea-webhook
      key: secret
EOF
----

The service skeleton is real engineering: source, tests, a root `Dockerfile`, a deployment manifest with probes, limits, and a hardened security context, and `.tekton/on-push.yaml` — the pipeline, reviewed and versioned like any other code. If anything strays from the golden-path contract, say so in the agent's channel and it will push the fix; when you are satisfied, **merge** — the merge is the push event that fires the build.

== Exercise 4: Register the service behind the gateway

The service is live. At this point, no agent knows it exists. Making it callable as a governed tool takes two declared resources — both in *your* namespace, both within your own RBAC: an HTTPRoute that attaches the service to the shared MCP gateway, and an MCPServerRegistration that tells the gateway to discover its tools. Same authorization path, same audit line, same trust model as every governed call in this lab.

. Create both resources:
+
[source,bash,role="execute",subs="+attributes"]
----
cat <<EOF | oc apply -n {user}-agent-workspace -f -
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: order-metrics-mcp-route
spec:
  hostnames:
    - {user}-order-metrics.mcp.local
  parentRefs:
    - group: gateway.networking.k8s.io
      kind: Gateway
      name: mcp-gateway
      namespace: agent-office
      sectionName: mcps
  rules:
    - backendRefs:
        - kind: Service
          name: order-metrics
          port: 8080
      matches:
        - path:
            type: PathPrefix
            value: /
---
apiVersion: mcp.kuadrant.io/v1alpha1
kind: MCPServerRegistration
metadata:
  name: {user}-order-metrics
spec:
  path: /mcp
  prefix: {user}_orders_
  state: Enabled
  targetRef:
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: order-metrics-mcp-route
EOF
----
+
Read what you just declared: the route attaches your service to the platform's `mcp-gateway` (its listeners deliberately admit routes from any namespace — attachment is the tenant's declaration, the gateway stays the platform's control point), and the registration names the route, the `/mcp` path your dev agent implemented, and the `{user}_orders_` prefix that namespaces your tools on the shared gateway. The prefix carries your seat name *on purpose*: every seat in this room is shipping a service with the same two tool names, and the gateway refuses a registration whose tool names collide with one already registered — the prefix is the tenancy boundary on a shared gateway, and yours has to be yours.

. Watch the gateway discover the tools:
+
[source,bash,role="execute",subs="+attributes"]
----
oc get mcpserverregistration {user}-order-metrics -n {user}-agent-workspace \
  -o jsonpath='{.status.conditions[0].reason}: {.status.conditions[0].message}{"\n"}'
----
+
Within about 30 seconds: `Ready: server added successfully. Total tools added 2. Total prompts added 0` — the gateway walked your route, spoke MCP to the service the factory built, and found `metrics_stuck_orders` and `metrics_weekly_summary`.

. Confirm the tools are visible to your assistant. Open link:{mattermost_url}[Mattermost^], go to the `{user}-assistant` channel, and send:
+
[source,text,subs="+attributes"]
----
Discover your governed tools. Do any of them start with "{user}_orders_"?
----
+
The assistant's governed tool surface now includes `{user}_orders_metrics_stuck_orders` and `{user}_orders_metrics_weekly_summary` — the service your dev agent shipped an hour ago, already indistinguishable in governance terms from the tools the platform shipped with.

== What just happened

AgentWorks ships a connector catalog. The list is fixed: the integrations the vendor chose to include, on the vendor's roadmap, installed on the vendor's timeline. Adding a connector means waiting for the vendor or filing a marketplace request.

What you built here works differently. The factory consumed a natural-language intent, scaffolded a service from a governed template, built a signed and scanned image through the TSSC (Trusted Software Supply Chain) pipeline, promoted it with OpenShift GitOps, registered it behind the MCP gateway, and exposed it as a new governed tool — one that did not exist in the catalog before Morgan asked for it. The requesting agent called it the same session. The catalog grew with the work.

The signed image carries an SLSA provenance attestation: the pipeline task that signed it recorded what inputs produced what outputs. Any operator can start at the tool call in Mattermost and trace back to the pull request the dev agent opened, to the scaffold skill the platform applied, to the intent Morgan posted. The supply chain is legible from end to end because every step produced an artifact on the platform ACME governs — not in a vendor's dashboard, not behind a vendor's API, not subject to a vendor's retention policy.

And notice what you rebuilt: `metrics_stuck_orders` is the tool your Module 4 skill declared as its dependency and your Module 5 pipeline called headless. The platform's own copy — the one you have been calling since Module 4 — was born exactly this way, from exactly this intent. The factory does not just run on the paved road; it paves it.

The MCP gateway is why the assistant agent could call a service that was not in the catalog when the lab started. The platform's trust boundary did not expand: same gateway, same authorization model, same per-call audit path. The catalog grew because you applied a resource to a namespace. On a vendor AI platform, that step is a support ticket. Here it is a `kubectl apply`.
