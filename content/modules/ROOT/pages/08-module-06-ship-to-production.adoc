The factory has been running since Module 1. You governed its tool calls in Module 3, taught it in Module 4, and ran it headless in a pipeline in Module 5. This module turns all of that into output: a shipped microservice, promoted to production, consumed as a new governed tool by the agent that originally asked for it.

The request comes from Morgan, ACME Financial's ops manager. Morgan needs a greeting-style lookup service. Old process: file a ticket, wait two weeks, follow up, wait more. Today's process: file an intent in Mattermost to a dev agent, watch the governed tool calls scaffold the service and open a pull request, merge it, and let the supply chain do the rest. The move that makes it Morgan's Monday: once the service is promoted to production, you register it behind the MCP gateway so the assistant agent Morgan already talks to can call it as a new governed tool, complete the original intent, and post the answer — all in Mattermost, all with an audit entry for every call.

5 exercises, about 60 minutes total. Each has a clean stopping point.

== Learning objectives

By the end of this module, you'll be able to:

* Hire a second agent from the same Developer Hub template and explain how a different brief composes a materially different capability set
* Commission a microservice through a Mattermost intent and trace the dev agent's governed Gitea tool calls to your org
* Read a supply-chain PipelineRun and confirm the build, sign, and scan stages completed before GitOps promoted the service
* Register a newly shipped service behind the MCP gateway using an MCPServerRegistration resource
* Trace the complete loop — a governed tool call from the requesting agent, through the gateway, to the service the factory just built — and read the audit entry that proves it happened

== Exercise 4: Register the service behind the gateway

The service is live. At this point, no agent knows it exists. To make it callable as a governed tool, you register it with an MCPServerRegistration resource. The gateway picks up the registration and exposes the service's endpoints as tool calls — routed through the same authorization, credential-injection, and audit path as every other governed tool in this lab.

. Create the registration resource:
+
[source,bash,role="execute",subs="attributes"]
----
cat <<'EOF' | oc apply -n {user}-agent-workspace -f -
apiVersion: openclaw.io/v1alpha1
kind: MCPServerRegistration
metadata:
  name: {user}-hello-service
spec:
  endpoint:
    url: http://hello-service.{user}-agent-workspace.svc.cluster.local:8080/mcp
  toolPrefix: hello
  gatewayRef:
    name: data-science-gateway-class
    namespace: agent-office
EOF
----
+
// AUTHOR NOTE (verify live): confirm the MCPServerRegistration CRD API version (openclaw.io/v1alpha1 or a newer version) and the exact spec field names (endpoint.url, toolPrefix, gatewayRef). Update the namespace in the URL to match where GitOps promoted hello-service. Confirm whether hello-service exposes a /mcp endpoint natively or requires a sidecar MCP adapter to be declared in the spec.
+
// AUTHOR NOTE (verify live): confirm the gatewayRef name (data-science-gateway-class is the current gateway class name — verify it has not changed since Module 3).

. Watch the gateway accept the registration:

== What just happened

AgentWorks ships a connector catalog. The list is fixed: the integrations the vendor chose to include, on the vendor's roadmap, installed on the vendor's timeline. Adding a connector means waiting for the vendor or filing a marketplace request.

What you built here works differently. The factory consumed a natural-language intent, scaffolded a service from a governed template, built a signed and scanned image through the TSSC (Trusted Software Supply Chain) pipeline, promoted it with OpenShift GitOps, registered it behind the MCP gateway, and exposed it as a new governed tool — one that did not exist in the catalog before Morgan asked for it. The requesting agent called it the same session. The catalog grew with the work.

The signed image carries an SLSA provenance attestation: the pipeline task that signed it recorded what inputs produced what outputs. Any operator can start at the tool call in Mattermost and trace back to the pull request the dev agent opened, to the scaffold skill the platform applied, to the intent Morgan posted. The supply chain is legible from end to end because every step produced an artifact on the platform ACME governs — not in a vendor's dashboard, not behind a vendor's API, not subject to a vendor's retention policy.

The MCP gateway is why the assistant agent could call a service that was not in the catalog when the lab started. The platform's trust boundary did not expand: same gateway, same authorization model, same per-call audit path. The catalog grew because you applied a resource to a namespace. On a vendor AI platform, that step is a support ticket. Here it is a `kubectl apply`.

== Learning outcomes

By completing this module, you should now understand:

* ✓ How the same Developer Hub template produces materially different agents, because the one-sentence brief drives catalog composition — the skill kit follows the stated job, not a preset role menu
* ✓ How a dev agent uses governed Gitea tools to scaffold a service, commit files, and open a pull request entirely through the governed tool path, with every call audited at the tenant-side ledger and the platform-side gateway log
* ✓ What the TSSC supply-chain pipeline does before a service is promoted: build, sign (SLSA attestation), and scan — in that order, blocking promotion on a failing scan
* ✓ How an MCPServerRegistration resource adds a shipped service to the gateway's tool catalog without changing the gateway's trust model or authorization path
* ✓ Why "the factory's output became the factory's new capability" is the structural difference from a vendor connector catalog: on this platform, the catalog grows with the work, every capability runs on infrastructure ACME governs, and provenance covers the full chain from intent to governed tool call
