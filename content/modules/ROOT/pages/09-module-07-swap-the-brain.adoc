The model is one field in the agent's manifest. Everything the agent is — its purpose, its skills, its governed tools, its git repository, its Mattermost channel — is unchanged by a model swap. Only the inference endpoint changes.

This module makes that concrete. You will edit the model reference from the frontier endpoint to a sovereign in-cluster vLLM served by OpenShift AI, watch OpenShift GitOps propagate the change, confirm the agent still performs the same way, and swap back. The mechanics are Module 2's edit loop: a commit to the agent's gitops repository, a pull request, a merge.

Plan on 20 minutes.

== Learning objectives

By the end of this module, you'll be able to:

* Locate the model reference in the agent's manifest and identify the endpoint it currently declares
* Change the model to a sovereign in-cluster vLLM by merging a pull request and confirm OpenShift GitOps propagated the change
* Verify that the agent's skills, governed tools, and git identity are identical after the swap
* Revert the model reference to the frontier endpoint with a git revert

== Exercise 1: Read the current model reference

The AgentWorkstation resource declares everything the agent runs with: system prompt, skills, tools, gateway, and model. You have read the first three fields in earlier modules. The model reference is the same kind of field — a value in `spec`, declared in `base/agentworkstation.yaml`, enforced by the operator.

. Confirm you are signed in as your lab user:
+
[source,bash,role="execute"]
----
oc whoami
----
+
Expected output:
+
[subs="attributes"]
----
{user}
----

. Read the model reference the agent is currently running with:
+
// VERIFIED LIVE 2026-08-25: the field is spec.model with two sub-fields — provider and modelName (current live value: provider openai-codex, modelName gpt-5.6-sol). The swap edits exactly those two fields.
+
[source,bash,role="execute",subs="attributes"]
----
oc get agentworkstation {user}-assistant -n {user}-agent-workspace \
  -o jsonpath='{.spec.model}'
----
+
The output names the current inference endpoint. It is a reference brokered through OpenShift AI Models-as-a-Service (MaaS, currently in early access) — not a credential the agent holds. The agent never receives a model provider key. MaaS manages provider access, per-user quotas, and rotation.

. Open the agent's repository — use the Source link in the Developer Hub catalog entry for `{user}-assistant`, as you did in Module 2. Navigate to `base/agentworkstation.yaml` and find the model field.
+
// AUTHOR NOTE (verify live): confirm the YAML field name and shape against a live deployed agent before publishing. The field is expected to be something like:
//   spec:
//     model:
//       endpoint: <maas-frontier-url>
//       modelId: <model-id>
+
NOTE: The model reference here and the gateway reference in Module 3 follow the same pattern: the manifest names the endpoint, MaaS or the gateway holds the credential, and the agent carries a reference. Swapping the model is changing the reference.

== Exercise 2: Swap to the sovereign endpoint

The sovereign endpoint is an in-cluster vLLM instance served by OpenShift AI and registered into the same MaaS broker. Changing to it means updating one field in the manifest and merging a pull request.

. In the agent's repository web UI, navigate to `base/agentworkstation.yaml` and click the edit icon.

. Find the model field and update its endpoint to the sovereign vLLM endpoint:

NOTE: The sovereign endpoint is an in-cluster vLLM registered into MaaS — same broker, different model on the other end. The agent's access is still brokered by MaaS; no new credential enters the agent's namespace.

. Commit the change to a new branch — use a name like `swap-to-sovereign` — and open a pull request to the main branch.

. Read the pull request diff before merging. The diff touches the model field. Every other field in the agent's spec is identical to what Module 1 created: same system prompt, same skills, same tools, same gateway reference.

. Merge the pull request.

. Open link:{gitops_url}[OpenShift GitOps^] and sign in with `{user}` / `{password}`. Find the Application named `{user}-agents-{user}-assistant-agent`.
+
The sync completes within seconds — by the time you switch tabs it may already show *Synced*. The evidence is in the Application's *History* tab: the revision listed there must match the commit you just merged.

. The agent pod does not restart for a model reference change. The operator re-renders the agent's configuration in place. Confirm the pod is still running, then read the model reference back from the cluster:
+
[source,bash,role="execute",subs="attributes"]
----
oc get pods -n {user}-agent-workspace
----

[source,bash,role="execute",subs="attributes"]

oc get agentworkstation {user}-assistant -n {user}-agent-workspace \

The reply arrives from the sovereign vLLM. The agent calls the same `gitea_*` tools through the same gateway, on your seat credential, as it always has. The answer is the commit you just merged — confirming the model, tools, and authentication chain all work together on the new endpoint.

== Exercise 3: Swap back

A model revert is a git revert. The same reconciliation loop that applied the swap applies the reversal.

. In the repository web UI, open the commit history for the main branch and find the merge commit from Exercise 2.

. Use the repository's revert button to create a revert commit on the main branch and merge it.
+
If you prefer the command line:
+
[source,text]
----
# Replace <repo-url> with the repository URL from the Developer Hub catalog entry.
git clone <repo-url>
cd <repo-directory>

# Find the merge commit hash.
git log --oneline -5

# Revert it. Replace <commit-hash> with the Exercise 2 merge commit hash.
git revert <commit-hash> --no-edit
git push origin main
----

. Open link:{gitops_url}[OpenShift GitOps^] and confirm the Application syncs against the revert commit. Check *History* — the latest revision should be the revert.

. Read the model reference from the cluster:
+
// AUTHOR NOTE (verify live): confirm jsonpath field path before publishing.
+
[source,bash,role="execute",subs="attributes"]
----
oc get agentworkstation {user}-assistant -n {user}-agent-workspace \
  -o jsonpath='{.spec.model}'
----
+
The frontier endpoint is back.

. Open link:{mattermost_url}[Mattermost^] and type `/new` in the `{user}-assistant` channel, then send the same task:
+
[source,text]

----
+
[source,text]

----
+
The reply arrives from the frontier endpoint. The answer is the revert commit — the newest entry in the repository.

== What just happened

AgentWorks offers model independence: choose a model from the vendor's approved list without changing anything else about your agents. That is a real capability, and you just exercised its equivalent — a single-field manifest change, reconciled by OpenShift GitOps, leaving every other agent attribute untouched.

Two things this platform does that a SaaS vendor cannot.

First: the agent held no model credential in either configuration. Both the frontier endpoint and the sovereign vLLM are registered in OpenShift AI Models-as-a-Service. MaaS manages provider keys, enforces per-user quotas, and rotates access. The agent carries a reference. This is the same pattern as Module 3's tool credentials: the agent holds what it needs to ask; the platform holds what it needs to act.

Second: you can run the model. The sovereign endpoint is a vLLM workload on the OpenShift cluster ACME already governs — the same cluster where the agents run, where GitOps reconciles, where the MCP gateway enforces tool access. Model weights do not leave ACME's infrastructure. Inference traffic does not cross a third-party network.

OpenShift is the platform ACME runs on AWS, on Azure, on GCP, and on-premise — the same operator-managed stack, the same governance model, the same governed-agents story regardless of where the hardware lives. Sovereign inference is not a datacenter-only option; it runs wherever OpenShift runs.

The AgentWorks model menu has edges. This platform does not have a menu in that sense: if the cluster can serve it, the agent can use it. Swapping between a frontier endpoint and a model ACME operates is a diff in git.
