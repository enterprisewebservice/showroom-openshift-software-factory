The brain is one reference in the agent's manifest. Everything the agent is — its purpose, its skill artifacts, its governed tools, its git repository, its Mattermost channel — is unchanged by a brain swap. Only which model answers changes.

When you hired your agent in Module 1, you picked its brain from a menu of *model connections* — brains the platform administrator published, each with an access list saying which roles may use it. You saw it drawn on the constellation's BRAIN ring. In this module you swap that reference: from the frontier Claude model on the platform's connection to a Red Hat-hosted open model, watch OpenShift GitOps propagate the change, confirm the agent still performs the same way, and swap back. The mechanics are Module 2's edit loop: a commit to the agent's gitops repository, a pull request, a merge.

Plan on 20 minutes.

== Learning objectives

By the end of this module, you'll be able to:

* Locate the brain reference — a model connection plus a model name — in the agent's manifest and read it back from the cluster
* Explain what a ModelConnection is and why the agent never holds a model provider credential
* Swap the agent to a Red Hat-hosted open model by merging a pull request, and confirm OpenShift GitOps propagated the change
* Verify that the agent's skill artifacts, governed tools, and git identity are identical after the swap
* Revert to the frontier model with a git revert

== Exercise 1: Read the current brain reference

The AgentWorkstation resource declares everything the agent runs with: system prompt, skill artifacts, tools, gateway, and brain. You have read the first four in earlier modules. The brain is the same kind of thing — fields in `spec.model`, declared in `base/agentworkstation.yaml`, enforced by the operator.

. Confirm you are signed in as your lab user:
+
[source,bash,role="execute"]
----
oc whoami
----
+
Expected output:
+
[subs="+attributes"]
----
{user}
----

. Read the brain reference the agent is currently running with:
+
// VERIFIED LIVE 2026-08-31: spec.model carries three sub-fields for a
// connection-based hire — connectionRef (the ModelConnection name),
// modelName, and provider (the literal `custom`, the vehicle for
// connection-keyed models). A Module-1 hire on the Claude connection
// reads: {"connectionRef":"claude-work","modelName":"claude-sonnet-5","provider":"custom"}
+
[source,bash,role="execute",subs="+attributes"]
----
oc get agentworkstation {user}-assistant -n {user}-agent-workspace \
  -o jsonpath='{.spec.model}'; echo
----
+
The `connectionRef` names a *ModelConnection* — a cluster-scoped resource the platform administrator published. The connection carries the endpoint and the credential reference; the agent carries only the connection's name and a model id. List the connections the platform publishes:
+
[source,bash,role="execute"]
----
oc get modelconnections
----
+
Each row is a brain on the hiring menu, and each declares which groups may pick it. Your seat sees the frontier connection you hired on (the frontier lane on the Red Hat work subscription) and the LiteMaaS connection (open models — {model_swap_family} — served by Red Hat's AI Services team). The administrator's personal lanes exist on the same cluster; your role simply cannot see them. Access is data, in git, like everything else here.

. Open the agent's repository — use the Source link in the Developer Hub catalog entry for `{user}-assistant`, as you did in Module 2. Navigate to `base/agentworkstation.yaml` and find the `model:` block.
+
NOTE: The brain reference here and the gateway reference in Module 3 follow the same pattern: the manifest names a reference, the platform holds the credential, and the operator projects it where it is needed. The agent's namespace never contains a model provider key. Swapping the brain is changing the reference.

=== Verify

* `oc get agentworkstation {user}-assistant -n {user}-agent-workspace -o jsonpath='{.spec.model}'` returns a value with a `connectionRef`
* `oc get modelconnections` lists the published brains, including the one you hired on and `{model_swap_connection}`
* The `model:` block in `base/agentworkstation.yaml` matches what the cluster reports

== Exercise 2: Swap to the Red Hat-hosted open model

The `{model_swap_connection}` connection fronts open models — {model_swap_family} — hosted by Red Hat's AI Services team and reached through the platform's model gateway. Swapping to it means updating the `model:` block and merging a pull request.

. In the agent's repository web UI, navigate to `base/agentworkstation.yaml` and click the edit icon.

. Replace the `model:` block so it reads exactly:
+
// VERIFIED LIVE 2026-08-31: this exact swap validated end to end —
// litemaas connection via the model-desk translator, Qwen3.8-27B
// answering (UNIFIED-OK probe). Qwen 3.8 is a reasoning model: it
// spends tokens thinking before it answers, so its replies can take
// a little longer than the frontier model's. That is part of the
// comparison.
+
[source,yaml,subs="+attributes"]
----
  model:
    provider: custom
    connectionRef: {model_swap_connection}
    modelName: {model_swap_model}
----
+
Leave every other field in the manifest exactly as it is.

. Commit the change to a new branch — use a name like `swap-to-qwen` — and open a pull request to the main branch.

. Read the pull request diff before merging. The diff touches the `model:` block. Every other field in the agent's spec is identical to what Module 1 created: same system prompt, same skill artifacts, same tools, same gateway reference.

. Merge the pull request.

. Open link:{gitops_url}[OpenShift GitOps^] and sign in
ifeval::["{seat_mode}" == "self-service"]
with the account you registered.
endif::[]
ifeval::["{seat_mode}" != "self-service"]
with `{user}` / `{password}`.
endif::[]
Find the Application named `{user}-agents-{user}-assistant-agent`.
+
The sync completes within seconds — by the time you switch tabs it may already show *Synced*. The evidence is in the Application's *History* tab: the revision listed there must match the commit you just merged.

. The operator now re-renders the gateway's model configuration: the `{model_swap_connection}` connection becomes a provider block on the gateway, with its key projected by the operator — never written into your namespace's manifests. A brain change restarts the gateway pod briefly so the new configuration loads. Watch it settle, then read the brain back:
+
[source,bash,role="execute",subs="+attributes"]
----
oc get pods -n {user}-agent-workspace
----
+
[source,bash,role="execute",subs="+attributes"]
----
oc get agentworkstation {user}-assistant -n {user}-agent-workspace \
  -o jsonpath='{.spec.model}'; echo
----
+
The output now names the `{model_swap_connection}` connection and the {model_swap_family} model.

. Test the agent with a task that requires governed tools. Open link:{mattermost_url}[Mattermost^], sign in as `{user}`, and find the `{user}-assistant` channel. Send `new session` first to start a clean session — a thread that replied from the frontier model carries history momentum for a turn or two, and the reset is deterministic (no slash: Mattermost swallows `/`-prefixed messages as its own commands):
+
[source,text]
----
new session
----
+
Then send the task:
+
[source,text]
----
Using your governed git tools: what is the latest commit message in your gitops repository?
----
+
The reply arrives from {model_swap_family}. The agent calls the same `gitea_*` tools through the same gateway, on your seat credential, as it always has. The answer is the commit you just merged — confirming the model, tools, and authentication chain all work together on the new brain. Expect the reply to take a little longer: {model_swap_family} 3.8 reasons before it answers.

== Exercise 3: Swap back

A brain revert is a git revert. The same reconciliation loop that applied the swap applies the reversal.

. In the repository web UI, open the commit history for the main branch and find the merge commit from Exercise 2.

. Use the repository's revert button to create a revert commit on the main branch and merge it.
+
If you prefer the command line:
+
[source,text]
----
# Replace <repo-url> with the repository URL from the Developer Hub catalog entry.
git clone <repo-url>
cd <repo-directory>

# Find the merge commit hash.
git log --oneline -5

# Revert it. Replace <commit-hash> with the Exercise 2 merge commit hash.
git revert <commit-hash> --no-edit
git push origin main
----

. Open link:{gitops_url}[OpenShift GitOps^] and confirm the Application syncs against the revert commit. Check *History* — the latest revision should be the revert.

. Read the brain reference from the cluster:
+
[source,bash,role="execute",subs="+attributes"]
----
oc get agentworkstation {user}-assistant -n {user}-agent-workspace \
  -o jsonpath='{.spec.model}'; echo
----
+
The frontier values are back.

. Open link:{mattermost_url}[Mattermost^] and send `new session` in the `{user}-assistant` channel, then send the same task:
+
[source,text]
----
new session
----
+
[source,text]
----
Using your governed git tools: what is the latest commit message in your gitops repository?
----
+
The reply arrives from the frontier model. The answer is the revert commit — the newest entry in the repository.

== What just happened

AgentWorks offers model independence: choose a model from the vendor's approved list without changing anything else about your agents. That is a real capability, and you just exercised its equivalent — a one-block manifest change, reconciled by OpenShift GitOps, leaving every other agent attribute untouched.

Three things this platform does that a SaaS vendor cannot.

First: *the brains are published, permissioned resources.* A ModelConnection is a cluster resource with an access list — the administrator publishes brains the way a platform team publishes golden paths, and your role determines your menu. Nobody handed you a key; you were granted access to a connection.

Second: *the agent held no model credential in either configuration.* The connection's credential lives in the platform's namespace and is projected by the operator onto the gateway. This cluster also runs OpenShift AI Models-as-a-Service (Tech Preview), which governs the same models for direct API consumers — per-user API keys, token budgets per group, and usage metering through one gateway. Model access here is a governed, metered, revocable grant — the same pattern as Module 3's tool credentials.

Third: *the swap crossed provider boundaries, not just model names.* The frontier model runs on a hyperscaler's infrastructure under a Red Hat subscription; {model_swap_family} is an open model served by Red Hat. Same manifest field, same governance, radically different supply chains. The next step on this path — an open model served by vLLM on this very cluster, published through OpenShift AI Models-as-a-Service — uses the same connection mechanics you just exercised: when the platform adds it, your swap target is one more row in `oc get modelconnections`.

OpenShift is the platform ACME runs on AWS, on Azure, on GCP, and on-premise — the same operator-managed stack, the same governance model, the same governed-agents story regardless of where the hardware lives.

The AgentWorks model menu has edges. This platform's menu is whatever the administrator publishes: frontier subscriptions, hosted open models, or models the cluster serves itself. Swapping between them is a diff in git.

By completing this module, you should now understand:

* ✓ Where the brain reference lives in the AgentWorkstation spec — a ModelConnection name plus a model id — and how to read it back with `oc`

* ✓ How the same governance covers frontier subscriptions and hosted open models — and extends to cluster-served models through OpenShift AI Models-as-a-Service
