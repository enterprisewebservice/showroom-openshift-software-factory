= Module 4: Teach with a mindifact

include::partial$_attributes.adoc[]

Your agent arrived knowing how to investigate and document. It did not arrive knowing your organization's procedures. On commercial agent platforms, the AgentWorks pitch for this capability is "skills/harness, supply-chain graded" — skill packs from the vendor's catalog, versioned however the vendor tracks them, installed on the vendor's timeline.

On this platform, know-how ships the way software ships. A *mindifact* is a versioned artifact in a registry: it has coordinates (`namespace/name:version`), a manifest, declared dependencies, and a content hash — and installing one is a declarative act your platform records. In this module you watch your agent fail at a task it was never taught, install a versioned pack that teaches it, and then trace the artifact's supply chain from registry coordinate to the running agent.

Plan on about 30 minutes.

== Learning objectives

By the end of this module, you'll be able to:

* Show that an agent's know-how is a defined, inspectable set — a pinned golden catalog plus whatever its namespace declares
* Install a versioned mindifact into your own workspace as a declarative resource and watch the agent learn it hands-free
* Verify the artifact's supply chain: registry coordinate, version, content hash, and declared dependencies
* Explain what separates a versioned, dependency-declared know-how artifact from a folder of markdown files

What it lacks is *your organization's procedure*: no severity classification, no fixed investigation order, no consistent structure another engineer could pick up. == Exercise 2: Inspect the artifact in the registry

The pack you are about to install exists as a published artifact in the platform's know-how registry — public, versioned, inspectable before you trust it.

. Read its registry index entry:
+
[source,bash,role="execute"]
----
curl -s https://mindifact.ai/v1/index.json | python3 -c "
import sys, json
for a in json.load(sys.stdin)['artifacts']:
    if a['name'] == 'platform-incident-triage':
        print(json.dumps(a, indent=2))"
----
+
Coordinates `agent-office/platform-incident-triage:1.0.0`, kind `skill`, a declared dependency (`mcpServer: ops-metrics`), and a declared capability (`ops.incident-triage`). Dependencies are *declared in the artifact*, not discovered by trial at runtime.

. Read the versioned content itself — the exact procedure your agent will follow:
+
[source,bash,role="execute"]

----
+
A fixed four-section reply structure, a P1–P4 severity rubric, a numbered investigation sequence. This URL is version-pinned: `1.0.0` in the path means this content, forever.

. Check the version history exists as a first-class record:
+
[source,bash,role="execute"]
----

== Exercise 3: Install it into your workspace

Installing a mindifact is declarative: a `Skill` resource in your namespace, carrying the artifact's full provenance — its registry, its coordinates, its content. Your agent's operator watches for exactly this.

. Apply the rendered artifact into your own workspace:
+
[source,bash,role="execute",subs="attributes"]
----
oc apply -n {user}-agent-workspace -f - <<'SKILL_EOF'
apiVersion: agentoffice.ai/v1alpha1
kind: Skill
metadata:
  name: platform-incident-triage
  labels:
    app.kubernetes.io/managed-by: agent-office
    agentoffice.ai/skill-tier: mindifact
  annotations:
    agentoffice.ai/registry: mindifact.ai
    agentoffice.ai/pack-ref: agent-office/platform-incident-triage:1.0.0
    agentoffice.ai/manifest: https://mindifact.ai/v1/platform-incident-triage/1.0.0/mindifact.json
    agentoffice.ai/content-url: https://mindifact.ai/v1/platform-incident-triage/1.0.0/skills/platform-incident-triage.md
spec:
  displayName: "Platform Incident Triage"
  description: "Triage a reported platform incident with a fixed severity rubric and a reproducible investigation sequence. Use whenever a user reports an outage, degradation, error, or \"something is broken\" on the cluster."
  version: "1.0.0"
  dependencies:
    - kind: mcpServer
      name: ops-metrics
  source:
    inline: |
      ---
      name: platform-incident-triage
      description: Triage a reported platform incident with a fixed severity rubric and a reproducible investigation sequence. Use whenever a user reports an outage, degradation, error, or "something is broken" on the cluster.
      ---
      # Platform incident triage
      
      When a user reports a platform incident, ALWAYS structure the reply with
      exactly these four sections, in this order, using these exact headings:
      
      ## Severity
      Classify using this rubric and state the classification with one
      sentence of justification:
      - **P1** — production service down or data loss in progress
      - **P2** — production degraded, or a non-production blocker with a deadline
      - **P3** — degraded with a workaround available
      - **P4** — cosmetic, informational, or a question
      
      ## What we know
      Bullet only the facts stated in the report or verified with tools.
      Never speculate here. If a fact is unverified, it does not belong in
      this section.
      
      ## Investigation sequence
      A numbered list, always in this order, scoped to the affected
      namespace: 1. pod status, 2. recent events, 3. logs of the failing
      workload, 4. recent changes (deployments, config, secrets). Name the
      exact command for each step. Run them through governed tools when
      available; otherwise name the command for the human.
      
      ## Next actions
      At most three bullets: the single most valuable next step first,
      who acts (agent or human), and what evidence would raise or lower
      the severity.
      
      Keep the whole reply under 250 words. No preamble before the first
      heading. Never fabricate command output: if a tool cannot answer,
      write "unverified" in What we know.
SKILL_EOF
----
+
NOTE: This YAML was rendered from the registry row — every annotation on it points back at the live artifact, which you can verify in Exercise 4. Rendering-and-applying is the client-side form of the platform's `/catalog/install`; a server-side install that targets your namespace directly is a named roadmap item.

. The resource is now part of your workspace's declared state:
+
[source,bash,role="execute",subs="attributes"]
----
oc get skills -n {user}-agent-workspace
----
+
One skill, with its VERSION column — `1.0.0` — straight from the artifact.

=== Verify

* `oc get skills -n {user}-agent-workspace` shows `platform-incident-triage` at version `1.0.0`

== Exercise 4: Watch the agent learn, then audit the supply chain

. The operator noticed your Skill the moment it landed and re-seeded the agent's workspace — no restart, no redeploy. Confirm:
+
[source,bash,role="execute",subs="attributes"]
----
oc exec deploy/{user}-assistant-gateway -n {user}-agent-workspace -c openclaw -- \
  ls /home/node/.openclaw/workspaces/{user}-assistant/skills/ | grep incident
----
+
And ask the runtime itself what it can now do:
+
[source,bash,role="execute",subs="attributes"]
----
oc exec deploy/{user}-assistant-gateway -n {user}-agent-workspace -c openclaw -- \
  openclaw skills list --agent {user}-assistant | grep incident
----
+
`✓ ready` — the runtime's own skill inventory lists your artifact, source `openclaw-workspace`, next to the baked set.
+
The union rule in one line: the baked image is the floor, your namespace's declared skills stack on top, and a name collision goes to the pinned image — the platform's set cannot be silently overridden.

. Now audit what you installed — four commands, each answering a question a supply-chain reviewer would ask:
+
*Where did this come from?*
+
[source,bash,role="execute",subs="attributes"]
----
oc get skill platform-incident-triage -n {user}-agent-workspace \
  -o jsonpath='{.metadata.annotations.agentoffice\.ai/pack-ref}'
----
+
*Is the content what the registry published?*
+
[source,bash,role="execute",subs="attributes"]
----
oc get skill platform-incident-triage -n {user}-agent-workspace \
  -o jsonpath='{.status.contentSha256}'; echo
curl -s "$(oc get skill platform-incident-triage -n {user}-agent-workspace \
  -o jsonpath='{.metadata.annotations.agentoffice\.ai/content-url}')" | shasum -a 256
----
+
// VERIFIED LIVE 2026-08-26: the operator populates status.contentSha256 on resolve for hand-applied CRs; both sides matched exactly (7e0b3b65…) on the first live run.
+
*What does it need?*
+
[source,bash,role="execute",subs="attributes"]
----
oc get skill platform-incident-triage -n {user}-agent-workspace \
  -o jsonpath='{.spec.dependencies}'
----
+
*And the golden set itself — who pins it?* Read the platform's lockfile: one entry per baked skill, each with an exact digest, closed by the digest of the composed catalog image. The compose run that builds it refuses to push unless the result is file-for-file identical to what shipped before — an equivalence gate.
+
[source,bash,role="execute"]
----
curl -s https://raw.githubusercontent.com/enterprisewebservice/agent-office/main/skills-image/skills-lock.yaml | head -20
----

=== Verify

* The workspace skills directory now contains `platform-incident-triage`
* `pack-ref` reads `agent-office/platform-incident-triage:1.0.0`
* `spec.dependencies` declares the `ops-metrics` mcpServer
* The lockfile shows per-skill digests and a composed-image digest

== What just happened

The AgentWorks pitch this module answers is "skills/harness, supply-chain graded." On commercial platforms of this class, a skill is a folder of instructions: you get whatever the marketplace serves today, with no version history you control, no content hash, no dependency declaration, and no way to pin what your agents run.

What you just did instead:

* *Published know-how as an artifact* — coordinates, version, manifest, declared dependencies, in a registry your platform federates
* *Installed it declaratively* — a resource in your namespace, carrying full provenance, applied with the same tool as any other platform change
* *Watched the operator deliver it* — hands-free re-seed, union over a digest-pinned golden set that an equivalence gate keeps honest
* *Audited the whole chain* — coordinate, content hash, dependencies, lockfile — with four commands

Know-how that ships like software can be reviewed like software, pinned like software, and rolled back like software. That is the supply-chain grade.

== Module summary

You taught your agent a procedure by installing a versioned artifact, and you can prove what was installed, where it came from, and what it depends on. Module 5 takes the same agent out of the chat window entirely: headless, inside a pipeline, with its autonomy set by platform policy.
