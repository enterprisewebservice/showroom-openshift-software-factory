The AgentWorks pitch for this module is "skills/harness, supply-chain graded." On a vendor platform, a skill pack ships from the vendor's catalog, versioned however the vendor tracks it, installed on a timeline the vendor controls. The version the agent runs is whatever the platform last deployed.

On this platform, a skill is a mindifact: a versioned Open Container Initiative (OCI) artifact published through the same supply chain as every other piece of software ACME governs. Every mindifact carries a content digest. The agent's declaration pins that digest. The cluster catalog checks it at runtime, and a skill that does not match its published artifact does not install.

In this module you give your agent a task it handles without a defined procedure, install a versioned mindifact through the Developer Hub Bindings card, and re-run the same task. The agent follows a procedure now. You will read that procedure in the workspace and trace the version pin back to its OCI artifact.

Plan on 30 minutes: establish a baseline, install the skill pack, confirm the behavior change, then inspect the artifact.

== Learning objectives

By the end of this module, you'll be able to:

* Confirm which skill packs are currently bound to your agent and explain what the workspace looks like before a new pack lands
* Install a versioned mindifact through the Developer Hub Bindings card and trace the resulting pull request through OpenShift GitOps to the agent's workspace
* Run the same task before and after a skill install and identify exactly where the agent's changed behavior comes from
* Read the skill's OCI digest in the agent's workspace and explain why version pinning makes know-how supply-chain graded

== What just happened

The AgentWorks pitch for this module is "skills/harness, supply-chain graded." On a vendor platform that phrase describes the vendor's catalog, the vendor's versioning, and the vendor's audit. Every part of the decision about what procedure an agent follows lives in the vendor's control plane.

What you did here is different at every step:

* *The mindifact is an OCI artifact.* It lives in the same registry as ACME's container images. The tooling that signs and scans a container image can sign and scan a skill pack. The policies that gate a container's promotion through environments can gate a skill's promotion through the same pipeline.

* *The install was a pull request.* A reviewer saw the diff before the agent's behavior changed. The diff was readable: pack name, version, digest. Merging was the moment of record — the same kind of moment as any other configuration change at ACME.

* *OpenShift GitOps enforced it.* The reconciliation loop that enforces ACME's application workloads enforced the skill install. Skill packs are not a separate concern from the cluster's declared state — they are part of it.

* *The version pin is mechanical, not documentary.* The digest in the manifest is not a note. The cluster checked it when the skill landed. A different artifact carrying the same pack name and version would not have installed. The procedure the agent followed is exactly the procedure that was published, at the declared version, verified at deployment time.

The gap with AgentWorks is not the behavior change itself — both platforms deliver that. The gap is the evidence trail: a PR with a readable diff, a merge commit with a named author, a GitOps sync against that commit, a digest check at install time. Everything ACME's platform and security teams need to answer "what procedure are our agents following, and when did that change."

The agent's behavior changed because the manifest changed. The manifest changed because a PR merged. The PR merged because a person reviewed the diff.
