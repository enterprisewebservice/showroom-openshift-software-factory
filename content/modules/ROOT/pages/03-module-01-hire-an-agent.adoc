ACME Financial wants what AgentWorks sells: AI development agents that deliver working software, not chat transcripts. The platform team vetoed the vendor pitch for 3 reasons. Credentials would leave the building. The audit trail would live in someone else's control plane. The software supply chain would answer to a vendor roadmap.

Your job in this lab is to prove ACME does not have to choose. You will build the same capability on the Red Hat OpenShift {ocp_version} cluster ACME already governs, then put it to work.

In AgentWorks terms, this module is onboarding a hosted agent. On this platform, the hire is a pull request: the agent is an OpenShift workload, and everything it receives (purpose, skills, tool access, and model) is declared in git before it runs. In about 2 minutes you will have a working agent, and you will be able to point at every object that made it exist.

Plan on 30 minutes: hire the agent, watch the platform onboard it, then read the wiring and make first contact.

== Learning objectives

By the end of this module, you'll be able to:

* Provision a governed AI agent from a Red Hat Developer Hub golden-path template
* Trace the objects the template created: a git repository, an OpenShift GitOps Application, an AgentWorkstation resource, and a catalog entry
* Map each form input (purpose, skills, gateway, and model) to the declared configuration the agent runs with
* Confirm the agent is live by sending it a message and reading its reply

== Exercise 1: Hire the agent

Hiring a developer at ACME takes weeks of process. Hiring an agent is 1 form, and the most important field is 1 sentence.

Red Hat Developer Hub is ACME's front door for anything a developer requests from the platform. Golden-path templates keep those requests inside guardrails the platform team defined. The agent template is exactly that: a governed way to say "staff this role."

ifeval::["{seat_mode}" == "self-service"]
. Open link:{devhub_url}[Red Hat Developer Hub^] and sign in with the account you registered.
endif::[]
ifeval::["{seat_mode}" != "self-service"]
. Open link:{devhub_url}[Red Hat Developer Hub^] and sign in as `{user}` with password `{password}`.
endif::[]

. In the left navigation, click *Catalog*, then click the *Self-service* button at the top right of the catalog page. This is the catalog of golden-path templates.

. Find the *OpenClaw Agent* template and click *Choose*.
+
// The dash in the template title below mirrors the live Developer Hub label verbatim.
You will also see *OpenClaw Agent (advanced -- every option)* in the list. That variant exposes every field the platform is about to wire for you: identity, model backend, skills, knowledge bases, gateway, deployment. This lab hires with the simple template and inspects that wiring after the fact, which is the point: the platform makes the safe choices so one sentence is enough.

. The form asks one question: *What will your agent be doing?* Write the brief you would give a new hire on day 1, and include the name you want the agent to carry:
+
[source,text,subs="+attributes"]
----
You are {user}-assistant, ACME Financial's platform assistant: investigate questions about this OpenShift cluster and document what you find.
----

. Click *Suggest*. The platform reads your brief and composes the hire: it picks the skills, tools, and knowledge it needs from the catalog, drafts the agent's identity, and wires the defaults — the gateway its tool calls route through and the model that serves as its brain. That catalog is federated live from the platform's artifact registry, where skills, governed tool definitions, and whole capability packs ship as versioned artifacts with declared dependencies — so Suggest assembles a working agent, not a list of files. The composed plan appears under the field. Read it: this is what you are about to hire. Skills are versioned know-how packs (Module 4 teaches with one). The gateway is a Model Context Protocol (MCP) gateway, the control point every tool call routes through (Module 3 governs it). The model is a swappable endpoint (Module 7 swaps it without touching anything else).
+
NOTE: The platform derives the agent's name from your brief. Naming it explicitly, as above, keeps the rest of this lab's commands aligned; if your agent ends up with a different name, substitute it wherever `{user}-assistant` appears.

. The composer keeps talking. Under your brief, the input becomes a short chat, and its first message asks whether the hire looks right. This is a conversation with the same brain that composed the hire, and it edits exactly what you ask: tell it to remove a specific skill and only that skill goes; ask it to add coverage for something and it adds the one artifact that covers it (plus anything that artifact requires). Questions are safe — ask one now:
+
[source,text]
----
is there a skill for incident response?
----
+
It answers from the live catalog and changes nothing until you tell it to. Every change you do make redraws the constellation and the wiring below in place — refining the composition, never regenerating it. When a suggestion is not quite right, this chat is the fix; rewriting the brief and starting over is the last resort, not the first.

. Check the composed skill list for `platform-incident-triage`. If the composer picked it, tell it to remove that one skill: `remove platform-incident-triage` — Module 4 teaches it to your agent deliberately, and the before-and-after there needs an agent that has not seen it. Only that row goes; everything else stays.

. Read the *constellation* that appears — the agent, drawn. The core is its identity; the BRAIN ring names its model; each skill artifact is a wedge of stadium rows where depth means how much it knows and hollow rim dots mean a capability whose cluster prerequisite is not deployed here; memory shows the seeded workspace documents; tools and the team orbit outside. Click anything for details — artifacts marked *»* open into their own orbit (double-click), showing what is inside a bundle. You will meet several of these rings again: Module 3 governs the tools, Module 4 teaches with a skill artifact, Module 7 swaps the brain.

. In the *Brain* section, a connection is already selected: the platform pre-selects its default brain for your role, and you keep it unless your host says otherwise. Under each connection sit the models it publishes — the first is its default, and clicking another changes it. The menu is not hardcoded: each entry is a *model connection* the platform administrator published with an access list, so the brains you see are the brains your role is granted. Module 7 swaps this reference without touching anything else.

. Click *Review*, check the summary of what Suggest composed, and click *Create*.

The template run executes in front of you. It creates a git repository for the agent, registers the agent in the catalog, and hands the rollout to Red Hat OpenShift GitOps.

== Exercise 2: Watch the platform onboard your hire

The template did not deploy anything itself. It wrote the agent's configuration to git and created an OpenShift GitOps Application that points at it. OpenShift GitOps (Argo CD under the hood) reconciles continuously: it reads the repository and makes the cluster match. The repository is the employment contract; the cluster is its current enforcement.

ifeval::["{seat_mode}" == "self-service"]
. Open link:{gitops_url}[OpenShift GitOps^] and sign in with the account you registered.
endif::[]
ifeval::["{seat_mode}" != "self-service"]
. Open link:{gitops_url}[OpenShift GitOps^] and sign in with your OpenShift credentials (`{user}` / `{password}`).
endif::[]

. Find the Application for your agent (search for `{user}-assistant`) and open it. Watch the resource tree while it syncs: the namespace, the AgentWorkstation resource, and the supporting objects appear as OpenShift GitOps applies them.

. In the terminal, confirm who `oc` is working as:
+
[source,bash,role="execute"]
----
oc whoami
----
+
ifeval::["{seat_mode}" == "self-service"]
It prints `system:serviceaccount:showroom-{user}:showroom-{user}` — your workbench's service account, an administrator of your project and nothing else, with a session that never expires.
endif::[]
ifeval::["{seat_mode}" != "self-service"]
It prints `{user}`; if it does not, complete the login steps from the lab details page before continuing.
endif::[]

. Watch the agent pod start:
+
[source,bash,role="execute",subs="+attributes"]
----
oc get pods -n {user}-agent-workspace
----
+
NOTE: Your agent runs in your own namespace, `{user}-agent-workspace` — nobody else's agents share it. It carries exactly the name you declared in your brief. `oc get agentworkstations -n {user}-agent-workspace` lists precisely one workstation: yours.
+
Re-run the command until the pod reports `Running`. The first start pulls the agent image, so allow a minute or 2. Expected output (the hash suffixes will differ):
+
[subs="+attributes"]
----
NAME                                      READY   STATUS    RESTARTS   AGE
{user}-assistant-gateway-c77bb699b-dzv5q  1/1     Running   0          2m
----
+
The pod is named after the agent's gateway — the runtime your agent lives in. `READY` counts its containers: `1/1` for a brain served through a model connection, `2/2` when a subscription brain adds a credential-sync sidecar. It is normal to see this pod replaced once shortly after first start (the AGE resets): the operator finishes wiring the model credential and restarts it one time.

== Exercise 3: Read the wiring and make first contact

On a vendor control plane, you trust that onboarding happened correctly. Here you can read it. Everything you granted in the form is now a declared field on 1 Kubernetes resource, and the catalog shows the same wiring to every developer at ACME.

. In Developer Hub, open the *Catalog* and find `{user}-assistant`. Open the entry and review what the platform recorded about your hire: its purpose, the skills you granted, the gateway it calls tools through, and the model it thinks with.

. In the terminal, list the AgentWorkstation resources in your agent namespace:
+
[source,bash,role="execute",subs="+attributes"]
----
oc get agentworkstation -n {user}-agent-workspace
----
+
Your agent appears in the list.

. Read the full resource the template created:
+
[source,bash,role="execute",subs="+attributes"]
----
oc get agentworkstation <your-agent> -n {user}-agent-workspace -o yaml
----

. In the `spec`, find the values that came from your form: the purpose sentence you wrote, the skills you granted, the gateway reference, and the model reference. Nothing else configured this agent. What you granted is what it has.

. Make first contact. Open the agent's chat channel and send it a message:
+
[source,text]
----
Introduce yourself. What is your purpose, and which skills were you hired with?
----
+
The template created the channel at hire time: open link:{mattermost_url}[Mattermost^], sign in as `{user}`, and find the channel named after your agent — it is in the left sidebar under *Channels* (you land in Town Square first; the system join messages there are just onboarding noise).

. Read the reply. The agent answers in its channel, and its answer reflects the purpose sentence and the skills you saw in the resource.

== What just happened

The form produced 4 objects. Together they are the entire hire:

* *A git repository*: the agent's workspace and configuration, and the source of truth. Changing the agent means changing this repository. Module 2 does exactly that with a pull request.
* *An OpenShift GitOps Application*: continuous reconciliation from the repository to the cluster. The rollout you watched was not a deploy script, and it never stops enforcing what git declares.
* *An AgentWorkstation resource*: the Kubernetes declaration of the agent itself. The platform operator turns this declaration into the running pod you watched start.
* *A Developer Hub catalog entry*: the staff directory record. Anyone at ACME can see who this agent is, what it can do, and how it is wired.

Note what is missing. The form never asked for credentials, and none were delivered to the agent. Tool access is a reference to a gateway, not a bundle of secrets. Module 3 proves that claim by searching the agent's environment for credentials and finding none.

The AgentWorks comparison is direct: onboarding a hosted agent and hiring this agent both take about 2 minutes. The difference is where the artifacts live. Here, every object above sits on ACME's cluster, in ACME's git, under ACME's RBAC, backup, and audit. There is no vendor control plane in this story.

By completing this module, you should now understand:

* ✓ How a Developer Hub golden-path template turns "hire an agent" into a governed, repeatable request
