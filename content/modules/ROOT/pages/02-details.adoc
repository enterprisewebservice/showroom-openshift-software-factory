= Prerequisites and environment

include::partial$_attributes.adoc[]

Everything in this workshop runs in your browser and on the lab cluster. Nothing installs on your laptop. This page covers what you need to know coming in, what is already running, how to sign in to each console, and what is yours alone.

== What you need to know

This is an intermediate lab for platform engineers, architects, and technical sellers. You should be comfortable with:

* OpenShift or Kubernetes basics: projects, pods, operators, and custom resources
* Git workflow: branch, commit, and merge a pull request
* Terminal work: every command is provided and explained, but you run it yourself

You do not need an AI or machine learning background. That is the point of the lab: agents here are ordinary workloads, so if you can operate OpenShift, you can operate agents.

== Your environment

You work on a shared, multinode OpenShift {ocp_version} cluster with per-attendee identity and isolation. Attendee-specific things (your login, your projects, your agents) are yours alone. Platform services are shared and multi-tenant, the way a production agent platform would run.

[cols="1,2",options="header"]
|===
|Component |Role in this lab

|OpenShift {ocp_version} (multinode)
|The factory floor. Every agent, pipeline, and model endpoint in this lab runs as a workload on this cluster.

|Red Hat Developer Hub
|The front door. Hosts the agent catalog and the golden-path templates, including the "hire an agent" template you use in module 1.

|OpenShift GitOps
|Reconciles every agent and application to what git declares. In module 2 you change an agent by pull request and watch it converge.

|OpenShift Pipelines and supply-chain tooling
|Builds, signs, and scans everything that ships, including code an agent wrote. Module 5 runs a headless agent inside a PipelineRun.

|agent-office operator
|Turns AgentWorkstation, AgentGateway, and Skill custom resources into running agents. An agent is a declared object, not a pet process.

|MCP gateway
|Governed tool access, built on Red Hat Connectivity Link. Every agent tool call passes through it for per-call authorization, credential injection, and an audit line. The agent never holds a credential.

|Red Hat build of Keycloak
|Per-attendee identity. Your login is a Keycloak identity, and the same sign-on works across every console in this environment.

|Model serving
|An in-cluster vLLM endpoint (the sovereign brain) and a frontier model endpoint, side by side. Module 7 swaps an agent between them.
|===

=== Verify your access

Do this before module 1. It takes about 2 minutes.

. In the *Terminal* tab, sign in as yourself. The terminal starts out
authenticated as the lab environment's service account — the first command
you run makes it yours. Enter the password from *Your credentials* above
when prompted:
+
[source,bash,role="execute",subs="+attributes"]
----
oc login -u {user} {openshift_api_url}
----

. Verify who you are now:
+
[source,bash,role="execute"]
----
oc whoami
----
+
Expected output:
+
[subs="+attributes"]
----
{user}
----

. List your projects:
+
[source,bash,role="execute"]
----
oc get projects
----
+
You see only the projects you are entitled to. Other attendees' projects do not appear. That is the isolation model working, not a permissions problem.

. Open the *OpenShift Console* tab. When the console offers a choice of identity providers, pick *workshop* and sign in as {user} — or pick *factory-sso* to use the same single sign-on the other tabs use.

. Open the *Developer Hub* tab and sign in with the same credentials.

Success looks like:

* `oc whoami` returns `{user}` in the terminal
* The OpenShift console shows your projects and nothing else
* Developer Hub loads the software catalog

== Pre-installed versus what you create

Everything in the component table is running before you arrive. You never install platform pieces:

* OpenShift, Red Hat Developer Hub with its golden-path templates, OpenShift GitOps, OpenShift Pipelines with the supply-chain tooling, the agent-office operator, the MCP gateway, Keycloak with your user already in it, and both model endpoints

Everything you create during the lab belongs to you and runs under your identity:

* *Module 1:* an agent hired from the Developer Hub template, with its git repo, GitOps application, catalog entry, and running workstation pod
* *Module 2:* pull requests against your agent's repo, and a rollback
* *Module 3:* governed tool calls, and the audit lines they leave behind
* *Module 4:* a versioned skill pack installed on your agent
* *Module 5:* PipelineRuns carrying a headless agent task
* *Module 6:* a production microservice: scaffolded by your dev agent, built and signed by the pipeline, promoted by OpenShift GitOps
* *Module 7:* a model swap on your own agent, frontier to sovereign and back

Module 8 is a guided comparison and creates nothing.

== Per-attendee isolation

* You sign in as {user}, a personal Keycloak identity honored by every console in the environment.
* Your work lands in your own projects. RBAC keeps other attendees' projects out of your view, and yours out of theirs.
* The agents you hire are yours: their repos, namespaces, workstation pods, and chat channels exist per attendee. Nobody else's prompts reach your agent.
* Shared services stay accountable. The MCP gateway records every tool call with the calling agent's identity, so shared never means anonymous.

== If something does not work

* The *Terminal* tab is blank or stops responding: reload the browser tab. The terminal reconnects to your session.
* `oc whoami` reports an error or the wrong user: re-run the `oc login` command from the verification steps.
* Keycloak rejects your password: confirm you are using the exact values from this page, because each attendee's credentials differ. If it still fails, tell your facilitator.
