The AgentWorks question for this module is straightforward: where does the hosted agent live? On a vendor platform, the answer is the vendor's control plane. On this platform, the answer is a git repository that ACME owns, on ACME's cluster.

You created that repository in Module 1, through the Developer Hub template. This module opens it, changes what is inside, and watches OpenShift GitOps carry the change to the running agent. Then it undoes the change the same way.

Plan on 25 minutes: tour the repository, change the agent's directive via a pull request, confirm the behavior changed, then roll it back.

== Learning objectives

By the end of this module, you'll be able to:

* Locate the agent's git repository from its Developer Hub catalog entry and identify its key files
* Modify the agent's behavior by editing its directive and merging a pull request
* Trace the reconciliation from a merged commit to a live behavior change on the cluster
* Roll back an AI agent's behavior with a git revert, with no vendor console and no support ticket

== Exercise 1: Tour the agent's repository

The template that ran in Module 1 created a git repository for your agent, named after it (`{user}-assistant-agent-gitops`) and linked from its Developer Hub catalog entry. The repository holds everything the agent is: a `base/` directory with the manifests that declare it as an OpenShift workload, deployment overlays, the Argo CD application, the catalog entry, and a `wiki-seed/` directory that seeds the agent's workspace.

. In the catalog entry, find the *Source* link and click it to open the agent's git repository.
+
NOTE: This is the repository the scaffolding run created at the end of Module 1. Everything the agent runs with is declared here.

. In the repository, open the `base/` directory and then `base/agentworkstation.yaml`. The `spec` section contains the values the platform wired in Module 1: the model reference, the gateway reference, and the skills. This is the same content you read with `oc get agentworkstation` in Exercise 3 of Module 1.

. In that file, find `spec.systemPrompt`.
+
This field is the agent's directive: the standing instructions it receives at the start of every conversation. The sentence you wrote in Module 1 is its seed. The job description is part of the workload manifest itself; there is no separate configuration store to drift out of sync.

----

Find `{user}-assistant` in the output and verify its `spec` matches the manifest you just read.

== Exercise 2: Change the agent's directive

A behavior change on a vendor AI platform is a toggle in someone else's control plane. Here it is a pull request: the diff shows exactly what changed, the review records who approved it, and the merge is the moment of record.

. In the repository's web UI, navigate to `base/agentworkstation.yaml`.

. Click the edit icon (pencil) to open the in-browser editor.

. Add the following line at the end of the `systemPrompt` block, indented to match the lines above it:
+
[source,text]
----
Always answer in exactly 3 bullet points. No more, no fewer.
----

. Commit the change to a new branch. Use a name you will recognize, such as `add-bullet-rule`.

. Open a pull request from that branch to the main branch.

. Read the pull request diff before merging. What you are reviewing is a proposed change to this agent's standing instructions: the `systemPrompt` is the job description the agent follows in every conversation.
+
NOTE: On a real team, this diff goes to a reviewer before the agent's behavior changes in production. Reviewing AI behavior changes is the same process as reviewing any other configuration change.

. Merge the pull request.

After the merge, OpenShift GitOps detects the new commit on the main branch and begins syncing. You do not need to trigger anything manually.

. Open link:{gitops_url}[OpenShift GitOps^] and sign in
ifeval::["{seat_mode}" == "self-service"]
with the account you registered
endif::[]
ifeval::["{seat_mode}" != "self-service"]
as `{user}` with password `{password}`
endif::[].

. Open the Application named `{user}-agents-{user}-assistant-agent`. Do not expect to catch it mid-sync: on this platform the automated sync typically completes within seconds of your merge, so by the time you switch tabs it usually already reads *Synced* again. The evidence is in *Last Sync* (open the Application's *History*): the synced revision matches the commit you just made.

. The agent pod does not restart for a directive change — and that is the point: the operator re-renders the agent's identity in place, in seconds, while the pod stays `Running`. Verify with the terminal instead of waiting on pods:
+
[source,bash,role="execute",subs="+attributes"]
----
oc get agentworkstation {user}-assistant -n {user}-agent-workspace -o jsonpath='{.spec.systemPrompt}'
----
+
The directive printed is the one you just merged.
+
[source,bash,role="execute",subs="+attributes"]
----
oc get pods -n {user}-agent-workspace
----

. Open link:{mattermost_url}[Mattermost^], sign in as `{user}`, and find the `{user}-assistant` channel. Send the same question from Module 1:
+
[source,text]
----
Introduce yourself. What is your purpose, and which skills were you hired with?
----

. Read the reply. It should follow the new rule: exactly 3 bullet points, no more, no fewer.

== Exercise 3: Roll back the change

Rolling back an AI agent's behavior on this platform is the same operation as rolling back any other workload: a git revert. The same reconciliation loop that applied the change applies the reversal.

. In the repository's web UI, open the commit history for the main branch and find the merge commit from Exercise 2.

. Use the revert button in the web UI to create a revert commit targeting that merge. Accept the defaults and merge the revert.
+
If you prefer the command line, clone the repository and run:
+
[source,text,subs="+attributes"]
----
# Replace <repo-url> with the URL shown in the catalog entry.
git clone <repo-url>
cd <repo-directory>

# Find the merge commit hash.
git log --oneline -5

# Revert it. Replace <commit-hash> with the hash of the Exercise 2 merge commit.
git revert <commit-hash> --no-edit
git push origin main
----

. Return to link:{gitops_url}[OpenShift GitOps^]. The same loop runs — and just as fast: check the Application's *History* for a new sync against your revert commit rather than waiting to see a transition.

NOTE: The directive lives in the agent's identity, not in the conversation — but the conversation remembers itself. A chat thread that just produced several three-bullet answers may echo that style for a turn or two even after the rollback lands, because the model sees its own recent replies. That is history momentum, not the directive surviving: read the directive back with the `oc` command above to see the enforced truth. For a clean-room proof, send the message `new session` in the agent's channel — the agent confirms the conversation history is cleared, so the very next answer reflects the current directive with zero transcript behind it. (Spell it without a slash: Mattermost intercepts any message that starts with `/` as one of its own slash commands and never delivers it.)

. Confirm the agent pod stayed `Running` through the rollback — same pod, no restart, exactly as in Exercise 2:
+
[source,bash,role="execute",subs="+attributes"]
----
oc get pods -n {user}-agent-workspace
----

. Open link:{mattermost_url}[Mattermost^] and send the same question again:
+
[source,text]
----
Introduce yourself. What is your purpose, and which skills were you hired with?
----

. Read the reply. The bullet-point rule is gone. The agent's answer returns to its original form.

== What just happened

On a vendor AI platform, a hosted agent's configuration lives in the vendor's control plane. Changing it means opening the vendor's UI. Rolling it back depends on whether the vendor stored the previous version.

What you did here is structurally different. The agent's directive is a file in a git repository. Changing it is a pull request with a diff. Reviewing it is code review. Merging it is the moment of record. Reverting it is a git revert. Every step produces an artifact in the same system the rest of ACME's software uses: a commit, a pull request, a review comment, an audit log.

OpenShift GitOps propagated every commit to the cluster without a deploy command. The operator reloaded the agent when the workspace changed. You controlled the behavior by controlling the file.

The AgentWorks question for this module was "where does the hosted agent live?" The answer: in git, exactly where everything else at ACME lives.

By completing this module, you should now understand:

* ✓ How to locate an agent's configuration by following the catalog entry's Source link to its git repository
